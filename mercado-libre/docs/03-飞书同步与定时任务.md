# 03 · 飞书同步与定时任务

> 定档版（2026-08-19）。飞书多维表格的结构、同步机制、三个定时时间点、校验方式。
> 合并自：`看板设计-飞书导出与定时触发.md`（已归档）。

## 1. 飞书侧结构

- **一个多维表格（Bitable base）**，每个 **店铺×月份** 一个子表（表名格式由代码生成，勿手改）：

<!-- GEN:month_table_name:BEGIN -->
表名 = `{店铺} {YYYY}年{M}月`（如 `BA05 2026年8月`）
<!-- GEN:month_table_name:END -->

- **行 = 商品 × 日期**（每日快照累积；每天每个商品一行）。
- 新月份表**自动创建**（`ensure_table`）：只要同步时出现该月数据，表/字段/视图自动建好。
- 凭证：`feishu.env`（`FEISHU_APP_ID/SECRET` + `FEISHU_APP_TOKEN` + 表 ID），已 gitignore。

### 1.1 子表列（由代码生成，勿手改；来源 `backend/app/routers/bitable.py` FIELD_DEFS）

<!-- GEN:columns_table:BEGIN -->
| 分组 | 列 |
|---|---|
| 结构（文本） | 日期 / 店铺 / 商品 / SKU / 商品ID / 广告状态 / 同步时间 / 广告 |
| 商品信息（属性） | 变体 |
| 库存 | 已售 |
| 流量·自然vs付费 | 全流量总访问 / 自然访问占比(访问) / 自然销售额 |
| 广告·加投决策 | 广告花费 |
| 质量 | 体验分 |
<!-- GEN:columns_table:END -->

> 已删除（用户要求）：`销售额 / 订单数 / 佣金 / 物流`（销售额=自然销售额+广告收入 冗余；佣金/物流与 佣金/件、平台运费 重复）。
> 口径与公式见 `docs/02`。属性列（变体/原价/佣金率%/佣金件/平台运费/实际收入件/广告）同商品每天相同；销量/广告列是**当日**值。

### 1.2 行组装规则（`_daily_rows`）

1. `daily_snapshot` LEFT JOIN `product_variation`（按 store+item 聚合：标题 MAX / 库存 SUM / 价格 MIN / 体验分 MAX / …）
2. **过滤**：只保留 `日期 ≥ 上架日(date_created)`（上架前不显示，避免 00 行）
3. **补零行**：没有订单/广告的商品，每天也补一行（当日 0 + 当前库存/价格），保证店铺所有商品完整可见
4. **排序**：按「日」生成（day-major：第 1 天全部商品 → 第 2 天…），保证飞书默认视图按日期升序不乱序（飞书 API 不支持自动设置视图排序/分组）
5. **访客**：`_attach_daily_visits` 按商品拉 visits 按天；未定档日 → 置空
6. **派生列**：`_derive_metrics`（公式见 docs/02 §6）
7. 内部字段（`_full_date` / `_revenue` / `_commission` / `_shipping`）仅计算用，`_upsert` 时剔除不写入

## 2. 同步机制（窗口化、增量、历史冻结）

- **ML→SQLite**（`sync.run_sync(days_back=N)`）：只拉最近 N 天（默认 4，停机越久越大 ≤14）；窗口内**先删后插**（取消的订单/停投的广告及时消失），窗口外历史不动。
- **SQLite→飞书**（`bitable.sync_daily()`）：
  - **默认窗口 = 昨天~今天**（`SYNC_WINDOW_DAYS=2`）：今天实时刷新（已售/库存/现价），昨天在巴西 10:20 定档后补广告列；
  - **窗口外（历史行）永久冻结** —— 写入一次后不再动，时间戳不再变化；
  - 特例：本店在飞书还没有任何月份表（新店/迁移/重建）→ **全量补建** 快照最早一天~今天；
  - 停机多天：定时任务启动补跑时窗口自动扩大（`gap+1` 天，≤14），把漏掉的日子补建。
  - **diff 增量 upsert**：按 `(商品ID, 日期)` 对比飞书已有行，只创建缺失行、只更新确有变化的行（跳过 同步时间 等易变字段）→ 重复运行几乎 0 写入。
- 同步前自动刷新 token（ML access 6h；飞书 tenant token 2h 缓存）。
- 未定档日广告列显式置空（batch_update 省略字段不清空）。

## 3. 定时任务（APScheduler，跑在后端进程内，需常开）

用户指定的**三个时间点**，每个都执行「ML 增量拉取 → 飞书 diff 增量同步」（触发时间由代码生成，勿手改）：

<!-- GEN:schedule_table:BEGIN -->
| 任务 id | 触发时间（本地） | 北京时间 |
|---|---|---|
| `daily_update_cn_0850` | Asia/Shanghai 08:50 | 08:50 |
| `daily_update_cn_1350` | Asia/Shanghai 13:50 | 13:50 |
| `daily_update_ad_finalize` | America/Sao_Paulo 10:20 | 21:20 |
<!-- GEN:schedule_table:END -->

各时间点作用：

| # | 时间点 | 作用 |
|---|---|---|
| ① | 北京 08:50（=巴西前一天 21:50） | 早上看最新昨日数据 |
| ② | 北京 13:50（=巴西 02:50） | 午间刷新 |
| ③ | 巴西 10:20（广告 10:00 定档后，=北京 21:20） | 补全昨日广告列 |

- 拉取窗口 `days_back`：默认 4，按距上次成功运行天数自适应（`gap+2`，范围 4~14）——停机多天也能补上期间定档的广告。
- **开机补跑**：启动时若巴西已过当天最早更新点（02:50）且今天没成功跑过（`data/.daily_update_marker` 记录最近成功日期）→ 自动补一次。
- 日志前缀 `[scheduler]`；完成打印 `每日更新完成: 拉取N天 sync={…} 飞书区间=…`。

## 4. 接口

| 接口 | 说明 |
|---|---|
| `POST /api/sync?days_back=N` | ML→SQLite（默认 90 全量；定时增量 4） |
| `GET /api/sync/status` | 同步状态 |
| `POST /api/export/bitable/daily?store=&date_from=&date_to=` | SQLite→飞书全区间同步 |
| `POST /api/export/bitable/daily/verify` | **校验**：飞书实际记录 vs 本地期望，逐 (商品ID,日期) × 29 个数字列对比，输出 缺失/多余/值差 |
| `POST /api/export/bitable/daily/backfill?days_back=N` | 手动回填最近 N 天（定时任务内部同款） |

## 5. 已知边界 / 踩坑记录

1. 飞书 API **不支持**自动设置视图排序/分组（PATCH view 只认 filter_info/hidden_fields/hierarchy_config，sort/group 静默忽略）→ 靠创建顺序保证默认视图按日排列；用户可在 UI 点列头排序。
2. 飞书数字字段**有时返回字符串**（如 `'31'`）→ 日期键统一 `_day_num` 归一化，否则下次同步会重复建行。
3. 一个 base 至少保留 1 个子表（删最后一个会报 1254034）→ 重建前先建临时占位表。
4. 记录按商品补零会导致默认视图乱序 → day-major 生成已修复。
5. 属性列（库存/现价/体验分/广告）历史行**冻结**：窗口外行显示的是"最后一次同步时的值"，不再跟随当前值刷新；只有窗口内（昨天~今天）跟随刷新（见 docs/02 §1）。
6. 校验 `verify` 默认只校验窗口（昨天~今天）；窗口外冻结行不参与对比。
