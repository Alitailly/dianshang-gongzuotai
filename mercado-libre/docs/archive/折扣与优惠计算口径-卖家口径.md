# 折扣与优惠计算口径（最终定稿 · 卖家口径 · 2026-08-17 修订）

> 本文档记录「折扣/优惠」的**最终计算口径**，后续改动必须以此为准。
> **2026-08-17 修订**：价格读取改为 `prices` 端点，现价=促销价（折扣价），原价=挂牌价（标准价）。

## 0. 价格字段口径（2026-08-17 起）

| 列 | 取值 | 说明 |
|---|---|---|
| **原价** | API `prices` 端点 `type=standard` 的 `amount`（= `/items/{id}` 的 `price`，挂牌价/划线原价） | 卖家设置的标价 |
| **现价** | API `prices` 端点 `type=promotion` 的 `amount`（**折扣价**；无促销时=标准价） | **实际销售价**，买家看到的价格 |
| 优惠原因 | 促销价（prices 有 promotion）/ 平台活动（promotions 数组）/ 卖家划线价（原价>现价）/ 空 | 按优先级识别 |

- **读取位置**：`src/atoms/products.py` `get_detail` 额外请求 `/items/{id}/prices`，取促销价作为 `effective_price`，标准价作为 `effective_original_price`；`extract_variations` 用这两个值入库。
- **背景**：`/items/{id}` 的 `price` 只返回标准价（可能打折前），实际售价在 `/items/{id}/prices` 的 `promotion.amount`（如 Morsa 标准 470 → 促销 285；AW12404 标准 28.71 → 促销 29.9）。之前只读标准价导致"现价"显示打折前价格，**已修复**。

## 1. 核心原则：只算「卖家自己设置的优惠」，平台波动不进表格

- **折扣只按卖家自设价格计算**：原价（挂牌价） vs 现价（折扣价）。
- **不读取平台波动价格**（订单实付价 `unit_price`、优惠券、平台补贴促销）——它们会因平台优惠/用户优惠券而波动，混入会污染表格口径。
- 原因：平台出资的优惠**不影响卖家利润**（ML 补贴差额），只有卖家自己让的利才是真正从收入里扣的。

## 2. 计算口径

```
折扣率(%) = (1 − 现价 ÷ 原价) × 100    （原价 > 现价 才计算，否则 0）
优惠原因 = 「促销价」/「平台活动：xxx」/「卖家划线价」（原价 > 现价）/ 空
折扣总额 = 订单级原价合计(gross_amount) − 销售额(revenue)
```

| 列 | 取值 | 说明 |
|---|---|---|
| 原价 | API `prices.standard.amount`（挂牌价） | 卖家设置的标价 |
| 现价 | API `prices.promotion.amount`（折扣价） | 无促销时=标准价 |
| 折扣% | (1 − 现价 ÷ 原价) × 100 | **纯卖家口径** |
| 优惠原因 | 促销价 / 平台活动 / 卖家划线价 / 空 | 平台促销/优惠券**不统计** |
| **折扣总额** | Σ(订单级原价 × 数量) − 销售额 | **所有渠道让的利合计**（含平台补贴与自己让的），按时间段累计 |

- 实现位置：`backend/app/repository.py` `_compute_ratios` 的 `discount_rate` / `discount_reason` / `discount_total`。
- **没有 `original_price` 的商品**：折扣% 与优惠原因不显示（卖家没设划线价），但**折扣总额照常计算**（它来自订单 gross_price，不依赖划线价）。
- 折扣总额的数据源：订单 `gross_price`（订单级原价合计）逐日累计存于 `daily_snapshot.gross_amount`。

## 3. 为什么不用「成交价/订单实付」

| 因素 | 影响 |
|---|---|
| 平台出资促销（Deal/闪购/自动比价） | 实付被拉低，但**不影响卖家利润**（平台补差额） |
| 用户优惠券（coupon） | 实付被拉低，来源可能是平台或卖家 |
| 自己设的划线折扣 | 实付 = 挂牌价，卖家利润真实减少 |

如果按实付（成交价）算折扣，会把平台补贴的部分误算成"卖家让利"，**低估卖家收入/利润**。所以订单实付价只在数据聚合时用于销售额/结算（真实到账口径），**不参与折扣计算**（收支·盈利列已按用户要求从商品分析页移除，暂不展示销售额/结算）。

> 注：订单接口里有 `gross_price`（订单级原价）、`unit_price`（实付）、`coupon`（优惠券）字段，daily_snapshot 也已存了这些列——保留用于未来分析，但当前表格折扣不读取它们。

## 4. 佣金/运费口径（2026-08-17 补充）

- **佣金率%** = 平台佣金 ÷ 销售金额 × 100（与美客多后台"销售费用占%"同口径；费率恒定，不随销量/批发价波动）。
- **佣金率%** = **官方精确费率**：`GET /sites/{site}/listing_prices?category_id=&price=&currency_id=&logistic_type=&shipping_mode=` 返回的 `sale_fee_details.percentage_fee`（按 类目+价格+物流 精确计算，如 AW13804=16.5%，与后台/订单一致）。
  - **2026-08-18 修正**：之前用 `/sites/MLB/listing_types/{id}` 的 `sale_fee_criteria`（gold_pro=16%），是类目基准不精确（实测 16.5%）。已改用 `listing_prices` 精确端点；无精确值时 fallback 到 listing 基准。
- **佣金/件** = 最近成交价(`last_price`) × 佣金率%（有实测用实测费率，无销量用官方费率×现价估算）——反映当前实际卖一件扣多少佣金。
- **平台运费（卖家承担口径，2026-08-18 修正）**：`/items/{id}/shipping_options` 的真实发货选项，按**承担方**区分（`shipping_payer`）：
  - **buyer（买家承担）**：`cost>0` 买家付运费 → 卖家实付 **0**，表格显示「买家付」（我们基本是买家承担）；
  - **meli（平台包邮）**：`free_shipping=true` 或 tags 含 `mandatory_free_shipping` → 卖家 0，显示「包邮」；
  - **seller（卖家承担）**：`cost=0` 买家不付 → 卖家付 `base_cost`（平台成本价）。
  - 此前误用 `/users/{uid}/shipping_options/free` 的 `list_cost`（买家全价估算），导致买家承担商品显示巨额运费（如 BA11115 39.9）。已修正。
- **实际收入/件** = 最近成交价 − 佣金/件 − 运费成本（包邮则运费=0）；未上架/未卖出显示对应标记。
- **已删除「平均物流/件」列**（历史订单算的，非官方数据源，用户要求移除）。
- **物流/件** = 区间物流总额 ÷ 区间销量（平均每件运费）；**无价格 = 没卖出去** → 显示「未卖出」。
- **实际收入/件** = 区间结算金额 ÷ 区间销量；未上架/未卖出显示对应标记。
- **商品三态**（`item_status`）：normal(上架有销量) / unsold(上架未卖出，佣金率有官方值，物流无) / offline(未上架，佣金/运费均标记「未上架」)。

## 5. 已知边界

1. 没有划线价的商品不显示折扣（卖家没设置，无从计算"自己的优惠"）；
2. 折扣反映卖家**当前**的原价 vs 现价（价格字段是当前值，随促销变化）；
3. 若想看清"买家实际付了多少 / 平台补贴了多少"，可另做分析视图（如订单明细/成交价列），但**不混入主表格的折扣口径**。
