# 看板设计 · 按店铺导出 CSV 到飞书 + 定时/条件触发

> 目标：把商品分析数据**按店铺导出 CSV**，自动发送到飞书群；后续支持**定时触发**与**条件触发**。
> 状态：设计稿（2026-08-19），待用户确认接入方式后实施。

## 1. 飞书接入方式（三选一）

| 方案 | 说明 | 能否发文件 | 复杂度 |
|---|---|---|---|
| **A. 飞书自建应用（推荐）** | app_id + app_secret → `tenant_access_token` → 上传文件 → 发文件消息到群 | ✅ 完整支持 | 中 |
| B. 自定义机器人 Webhook | 只有群 webhook URL，能发文本/卡片/图片；**发文件仍需要 app 凭证先上传拿 file_key**（webhook 本身不能上传） | ⚠️ 只能发通知卡片+摘要 | 低 |
| C. 飞书多维表格 Bitable | 按行导入多维表格，结构化，适合后续分析/筛选 | ✅（表格形式） | 高 |

**推荐 A**：一次配置 app 凭证，即可发"文件消息"（群成员直接下载 CSV），也兼容后续发文本摘要卡片。

### 方案 A 的 API 流程（官方）
1. **拿 token**：`POST /open-apis/auth/v3/tenant_access_token/internal`（app_id, app_secret）→ `tenant_access_token`（2 小时有效，本地缓存）。
2. **上传文件**：`POST /open-apis/im/v1/files`（multipart：`file_type=stream`、`file_name=商品分析_BA05_xxx.csv`、文件流）→ `data.file_key`。
3. **发文件消息**：`POST /open-apis/im/v1/messages?receive_id_type=chat_id`，body `{"receive_id": "<群 chat_id>", "msg_type": "file", "content": "{\"file_key\": \"...\"}"}`。
4. **拿群 chat_id**：把机器人拉进群后，`GET /open-apis/im/v1/chats` 查（或用户提供群链接/群名）。

### 方案 B 的替代做法
若用户只有 webhook（不想建应用）：每次发送时在群里发一张**摘要卡片**（各店铺 已售/库存/广告花费/ROAS 等几个关键数字），CSV 仍在看板手动下载。适合"只想要个提醒"的场景。

## 2. 按店铺导出

- 复用现有 `GET /api/export/products.csv?store=BA05&date_from=…&date_to=…`（已含中文表头+BOM+CRLF）。
- 循环店铺：`ba05`(BA05)、`store2`(AW04) → 每个店铺一个 CSV。
- 文件名：`商品分析_{店铺名}_{date_from}_{date_to}_{时间戳}.csv`（如 `商品分析_AW04_2026-07-19_2026-08-17_20260819-2100.csv`）。
- 店铺 → 群映射（配置表/文件）：`{"BA05": "oc_xxx", "AW04": "oc_yyy"}`；未配置的店铺跳过。

## 3. 触发方式（分阶段落地）

| 阶段 | 触发 | 说明 |
|---|---|---|
| **① 手动**（先做） | 看板"发送到飞书"按钮（按店铺 / 全店铺） | `POST /api/export/feishu?store=BA05`，后台同步导出→上传→发送，返回每店结果 |
| **② 定时**（后加） | APScheduler 每日固定时间 | 建议**巴西 10:00 后（= 北京 21:00）**跑：广告已定档、当天数据完整，导出的数最全；或用户自定义时间（如 08:00/12:30 中国时间） |
| **③ 条件**（后加） | 规则表触发 | 例：同步完成后自动发送；或某店 ROAS < 保本ROAS / 可售库存 ≤ 0 / 广告花费超阈值 → 只发告警摘要 |

### 定时/条件架构
- 后端用 **APScheduler**（FastAPI startup 注册）：`cron` 任务每天固定时间跑导出；`interval` 任务轮询条件。
- **同步挂钩**：`run_sync` 完成后可选自动触发发送（条件：数据已刷新）。
- 规则存配置表：`{store, metric, operator, threshold, action}`。

## 4. 配置与安全

- 飞书凭证（app_id/app_secret）、群 chat_id 映射、定时时间 → 放 `stores.d/` 同级的 `.env` 或 `config` 表（**本地工具，明文可接受，但建议不进 git**）。
- token 缓存 + 过期自动刷新；发送失败重试 1-2 次 + 日志。
- 文件内容即现有 CSV（商品/库存/流量/广告），无敏感财务信息外泄风险（按需确认）。

## 4.1 飞书应用需开通的权限（用户配置清单）

| 权限 Scope | 用途 | 必需 |
|---|---|---|
| `im:file` | 上传文件（`/im/v1/files`） | ✅ |
| `im:message` | 发送消息（`/im/v1/messages`） | ✅ |
| `im:message:send_as_bot` | 以机器人身份发送 | ✅ |
| `im:chat:readonly` | 自动查群 chat_id（可选，用户直接给 chat_id 可不开） | ⚠️ |

**步骤**：创建企业自建应用 → 启用机器人能力 → 权限管理开上述 scope → **发布版本（审批后生效）** → 把机器人拉进目标群 → 提供 app_id/app_secret + 群 chat_id。
**不需要**：事件订阅、`im:resource`（下载消息文件用）、`im:image`。

## 5. 实施步骤（确认后）

1. 后端加 `feishu.py`（get_token / upload_file / send_file / send_text）。
2. `POST /api/export/feishu`：按店铺导出→上传→发送，返回逐店结果；前端加"发送到飞书"按钮（按店铺/全店铺 + 状态提示）。
3. APScheduler 定时任务（配置时间，默认巴西 10:00 后）。

## 6. 实施进度（2026-08-19 更新）

### ✅ 已完成：多维表格每日同步（按店铺×月份分子表，用户拍板结构）
- **结构**：一个基内，**每个店铺×月份一个子表**（表名=`{店铺} {YYYY}年{M}月`，如 `BA05 2026年7月`）；行 = **商品 × 日期**（每日快照累积）。
- **每行字段**（2026-08-19 起与看板「商品分析」列对齐，同名同口径）：结构列 `日期`(文本 "MM-DD"，如 08-10；表名已含 店铺+年月，行内用 月-日 便于筛选查找，不重复年份) / `店铺` / `商品` / `SKU` / `商品ID` / `广告状态` / `同步时间` / `广告`(有/无) + 商品信息 `变体` `现价` `原价` `佣金率%` `佣金/件` `平台运费` `实际收入/件` + 库存 `已售` `可售库存` + 流量·自然vs付费 `全流量总访问` `自然访问(估算)` `广告点击` `曝光` `自然访问占比(访问)` `广告点击占比(访问)` `自然销售额` `广告收入` `自然销售额占比(销售)` `广告销售额占比(销售)` + 广告·加投决策 `广告花费` `ROAS` `保本ROAS` `ACOS%` `CTR%` + 质量 `体验分`。销量/销售额/广告列是**当日**值（表为每日明细），属性列（变体/原价/佣金率%/佣金件/平台运费/实际收入件/广告）同商品每天相同。~~销售额/订单数/佣金/物流~~ 已按用户要求删除（销售额=自然销售额+广告收入 冗余；佣金/物流与佣金/件、平台运费重复）。
- **广告 T+1 处理（用户要求的可读性方案）**：每行 `广告状态` = `已定档` / `未定档·广告预览`（按 `br_latest_finalized_date()` 判定）；**未定档日的广告列（点击/曝光/花费/收入）与全流量总访问显式置空**，只保留实时数据（已售/库存/价格），定档后再同步自动补全——避免"实时数据对、广告数据错"的误导。
- **上架日期过滤**：只保留商品上架日（`date_created`）之后的行，去掉上架前的大批 00（例：AW13804 8/7 上架，之前无行；BA05 商品 7/31 后才上架 → 无 6 月表）。
- **同步方式**：**增量 upsert**（按 商品ID+日期：存在→更新，不存在→插入）；全区间 BA05=242 / AW04=1054 行。
- **行顺序**：记录按「日」生成（day-major：第 1 天全部商品 → 第 2 天全部商品…），保证飞书默认视图按日期升序显示、不乱序（飞书 API 不支持自动设置视图排序/分组，只能靠创建顺序 + 用户可在 UI 点列头排序）。
- **视图**：每个子表只保留默认平铺「表格」视图，所有日期所有行直接可见；**不再自动创建「按日分组」视图**（用户反馈分组折叠导致看不全数据，2026-08-19 已删除全部 5 个表的分组视图并移除自动创建逻辑）。
- **接口**：`POST /api/export/bitable/daily?store=&date_from=&date_to=`；`POST /api/export/bitable/daily/verify`（校验，两店 OK）；`POST /api/export/bitable/daily/backfill?days_back=7`（手动回填最近 N 天）；`POST /api/sync?days_back=N`（ML 拉取窗口，默认 90 全量，每日增量 4 左右）。
- **每日自动更新（APScheduler，2026-08-19 起，用户指定三个时间点）**：每天三个点自动执行两步（ML 增量拉取 → 飞书全区间 upsert）：
  - **① 北京时间 08:50**（=巴西前一天 21:50）：早上看最新昨日数据
  - **② 北京时间 13:50**（=巴西 02:50）：午间刷新
  - **③ 巴西 10:20**（广告 10:00 定档后，=北京 21:20）：补全刚定档的昨日广告列
  - 每步：1️⃣ `sync.run_sync(days_back=N)`（N 默认 4、按距上次运行天数自适应最多 14 天；`daily_snapshot` 用 **upsert 增量更新**，已定档历史不重拉、不丢失）；2️⃣ `bitable.sync_daily()` 全区间（自动建新月份表、填新一天、补广告列、用当前库存/现价刷新所有历史行）。
  - 开机补跑：启动时若巴西已过当天最早更新点 02:50 且今天未跑过（`data/.daily_update_marker` 记录最近成功日期）→ 自动补一次。日志 `[scheduler]`。
- **踩坑修复**：① LEFT JOIN 变体多行翻倍→按 (store,item_id) 聚合；② ML token 6h 过期→同步前刷新；③ batch_update 省略字段不清空→未定档日显式置空；④ 商品上架前大批 00 → 按 `date_created` 过滤；⑤ 飞书数字字段返回字符串→日期键归一化；⑥ 记录按商品补零导致乱序→day-major 生成；⑦ daily_snapshot 删光重写会丢历史→改 upsert。
- 凭证在 `feishu.env`（已 gitignore）。
