# Spec：AI 功能集——广告助手 + 站内信消息工作台

> 状态：`ready-for-agent`（本地 tracker，2026-09-01）
> 词汇与决策依据：`CONTEXT.md`（R1-R15）。本 spec 使用其定档词汇。

---

## Problem Statement

卖家（用户）有两个运营痛点：

1. **广告数据没有变成行动**。广告指标已按天落在快照表里（花费/点击/曝光/CTR/销售额/ROAS/ACOS），看板能展示数字，但「数字」不等于「洞察」——每次都要自己对着报表想「哪里该优化、怎么优化」，缺乏系统性的分析和可落地的建议。
2. **买家站内信处理靠纯人工**。买家在 ML 平台发站内信（售前商品咨询 / 售后订单、物流、退款问题），卖家逐条手动回复耗时；但完全自动回复又有答错风险——回答错了直接发给买家，伤店铺信誉。

## Solution

为看板新增两个 AI 能力（共享一个 DeepSeek 底座）：

1. **广告助手**：看板新增「广告助手」页面。卖家选定店铺 + 时间范围 → 一键分析 → LLM 基于现有广告聚合数据输出「表现总览 + 3~5 条具体优化建议」，每条建议含问题、依据、行动。
2. **站内信消息工作台**：系统按固定间隔轮询拉取买家站内信 → LLM 为每条消息生成应答草稿 → **卖家在网页上校验/编辑草稿** → 确认后才通过 ML 消息 API 真正发回买家。售前（pre_sale）与售后（post_sale）消息由 ML 自带 tag 分流；草稿生成时售前读商品表、售后查订单/物流；多轮上下文取 pack 内完整消息历史。

## User Stories

1. 作为卖家，我想在看板导航里看到「广告助手」页面，以便一键获得广告数据解读。
2. 作为卖家，我想选择店铺（或全部）和时间范围后再分析，以便聚焦特定区间。
3. 作为卖家，我想看到所选范围的广告表现总览（花费/点击/曝光/CTR/销售额/ROAS/ACOS 的总结），以便快速了解全局。
4. 作为卖家，我想看到 3~5 条具体优化建议，每条含问题、数据依据、建议行动，以便直接落地执行。
5. 作为卖家，我想在分析失败时看到清晰提示（无数据 / LLM 调用失败），以便知道是调整范围还是重试。
6. 作为卖家，我想看到分析所用的数据时间范围（基于定时快照），以便不被陈旧数据误导。
7. 作为卖家，我想系统自动按固定间隔检查新站内信，以便不错过买家的任何消息。
8. 作为卖家，我想在「消息工作台」看到所有待处理消息，并按售前/售后区分，以便统一处理。
9. 作为卖家，我想看到每条消息所属 pack 的完整对话历史，以便了解来龙去脉。
10. 作为卖家，我想对消息一键生成回复草稿，以便快速应答。
11. 作为卖家，我想在草稿发出前校验、编辑它，以便防止错误回复（人审闸门）。
12. 作为卖家，我想只有确认后草稿才真正通过 ML API 发回买家，以便保证回复质量。
13. 作为卖家，我想标记不需要回复的消息为「跳过」，以便清理队列。
14. 作为卖家，我想追踪每条消息的状态（待审/已发/跳过），以便知道还欠哪些买家回复。

## Implementation Decisions

1. **LLM 底座（共享）**：后端新增 LLM 封装模块，统一 `chat(system_prompt, messages) → 文本` 接口。DeepSeek API key 从环境变量读取（进 `.env`，沿用密钥不入库先例），前端永不接触 key。广告助手与消息工作台共用此模块。超时/限流/解析失败有统一错误语义。
2. **广告助手**：新增服务模块——查询广告聚合数据（**复用现有 repository 查询**，不新造数据管道）→ 组装 prompt（含指标定义与「定档」语义说明）→ 调 LLM → 解析为结构化建议（总览 + 3~5 条建议，每条：问题/依据/行动）。新增 API 端点；前端新增独立页面，沿用现有 Vue3 + Element Plus + router 模式，不修改现有 4 个页面。页面展示分析所用数据时间范围。
3. **站内信接入层**：新增消息模块——拉取消息 packs、拉取 pack 内消息、发送回复。注意新消息架构：MLB/MLC 收件人使用国家 **agent ID**（非买家 ID）；消息按 `tag`（pre_sale/post_sale）区分。
4. **待审队列**：SQLite 新增消息工作台表，状态机 `new → draft → sent / skipped`。草稿、消息原文、pack id、状态、时间戳持久化。发送动作记录为最终状态，不可回改。
5. **轮询任务**：复用现有调度器新增定时 job（间隔约 5~10 分钟，spec 落地后定精确值），拉取新消息进入待审队列并自动生成草稿。
6. **草稿生成分流**：按消息 tag 分流——售前草稿以上下文 = 商品信息（product_variation 的商品标题/价格/库存/规格/运费/发货口径）组装；售后草稿以上下文 = pack 内历史 + 实时订单/物流查询结果（新增单订单/单物流查询封装，模式复用现有订单拉取，非聚合）。
7. **多轮上下文**：草稿生成时拉取 pack 内完整消息历史作为对话上下文（后端无状态，历史来自 ML API）。
8. **人审闸门**：任何消息的发送都需人工在网页确认；系统不做任何自动发送。
9. **前端消息工作台**：新增页面——消息列表（售前/售后筛选、状态筛选）+ 对话视图（pack 历史）+ 草稿校验区（生成/编辑/确认发送/跳过）。

## Testing Decisions

- **测试基建**：后端引入 pytest（当前项目零测试，基建本身是引入项）。前端第一版不引入测试（现有前端零测试，保持）。
- **测试接缝**（已与用户确认，3 个，全部在后端，外部依赖用假替身注入）：
  1. **LLM 客户端**：注入 fake LLM（固定返回），验证 prompt 组装、建议 JSON 解析、错误/超时处理。
  2. **广告助手服务**：fake LLM + 内存 SQLite（复用现有 repository 查询逻辑），验证输出结构（总览 + 建议卡片字段）与 prompt 内容包含关键数据。
  3. **消息工作台服务**：fake ML 客户端 + fake LLM + 真实 SQLite 表，验证完整状态流（收 → 草稿 → 确认 → 发 / 跳过）、tag 分流、多轮上下文组装、待审队列持久化。
- **只测外部行为**：验证输入/输出契约与状态转移，不测实现细节。现有 `repository.py` 查询函数作为数据来源使用。

## Out of Scope

- FAQ / 店铺政策知识库（第一版不做）
- 广告建议写入 `ad_ops_log`（第一版只读分析）
- 广告助手对话式追问（第一版一次性分析）
- 飞书渠道的客服消息
- 买家公开入口、消息自动发送（人审闸门永久保留）
- 多轮记忆持久化（pack 拉取即得，无需自建）
- 前端组件测试
- 广告/订单数据的新增采集管道（复用现有快照与查询）

## Further Notes

- **待实测**：现有 OAuth scope（`read write`）对消息 API 是否足够；新消息架构 MLB 的 agent ID 获取方式。实测失败则回退调整（补 scope 需重新授权店铺）。
- **数据新鲜度**：广告助手基于定时快照数据，页面必须展示数据时间范围，避免误读。
- **新消息架构**：消息端点带 `tag=post_sale` / `pre_sale` 参数，接入层需确认站点（MLB）语义。
- **错误路径**：LLM 调用失败 / ML 拉取失败时，消息保持「待审」，不丢单；页面可重试生成草稿。
